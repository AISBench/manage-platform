# AISBench PR / Issue 管理平台设计文档

- 文档版本：v1.0
- 日期：2026-11-11
- 状态：设计稿，供需求确认和后续开发使用
- 目标业务仓库：[AISBench/benchmark](https://github.com/AISBench/benchmark)
- 平台源码仓库：[Libotry/aisbench-triage](https://github.com/Libotry/aisbench-triage)
- 适用范围：单团队、单业务仓库、海外服务器与个人域名部署

> 核心方案：**管理员预先录入团队成员 → 成员使用 GitHub 登录 → 平台核验准入资格 → 成员自行授权绑定飞书 → 按责任关系接收提醒并跟进事务。**
>
> 本文保留设计编写时的需求与初版基线，不把设计条目自动视为已验收能力。后续 v0.2 的实际代码补齐、测试及未完成的目标环境验收，参见 [v0.2 验证记录](VALIDATION-V02.md)；海外正式部署仍未执行。

## 1. 背景与建设目标

AISBench 仓库的 PR、Issue 分散在 GitHub 页面和个人通知中，维护者难以及时判断谁负责、哪些事项等待处理、哪些事务已经积压。项目需要一个面向团队的网页管理平台，将仓库事件、责任人、处理进度和飞书个人提醒串成闭环。

### 1.1 业务目标

1. 集中查看 PR、Issue、评审请求、评论及 CI 状态。
2. 明确每项事务的平台负责人、优先级、处理阶段和截止时间。
3. 将 GitHub 身份与真实团队成员、个人飞书身份关联，精准提醒。
4. 通过事件通知、超期催办、管理员兜底减少遗漏。
5. 由管理员管理准入，无开放注册，无需维护账号密码。
6. 部署到用户已有的海外服务器，使用个人域名和 HTTPS 访问。

### 1.2 设计原则

- **身份认证与访问授权分离**：GitHub 确认“你是谁”，平台成员名单决定“能否进入、可以做什么”。
- **账号关联不靠自报**：GitHub 身份通过 OAuth 验证，飞书身份通过本人 OAuth 授权获取。
- **固定 ID 关联，用户名展示**：GitHub 用户名允许变化，不作为长期授权主键。
- **GitHub 与本地流程分离**：仓库状态由 GitHub 决定，平台处理进度独立保存。
- **默认最小权限**：仓库集成只读，提醒默认关闭，未录入或被停用的成员不得访问。
- **先可靠再扩展**：单实例、SQLite 持久化、事件入队、失败可重试；暂不引入复杂分布式基础设施。

## 2. 需求边界与设计决策

D01–D04 对应本次讨论确定的成员使用方式；其余条目是结合现有初版提出的范围与技术建议，权限细则、运维参数仍需实施前确认，不表示已经获得服务器操作或真实消息发送授权。

| 编号 | 决策 | 说明 |
| --- | --- | --- |
| D01 | 不开放自主注册 | 首次 GitHub 登录只激活预先录入的成员，不自动授予陌生账号访问权 |
| D02 | 管理员网页管理成员 | 新增、编辑、设置角色、停用、重新启用，不依赖每次修改服务器环境变量 |
| D03 | GitHub 是登录入口 | 不提供本地密码登录、邮箱找回密码 |
| D04 | 飞书由成员本人绑定 | 管理员查看绑定状态，不填写或冒用他人的飞书 ID |
| D05 | 先支持一个目标仓库 | 默认 AISBench/benchmark，平台源码仓库与业务仓库相互独立 |
| D06 | GitHub 操作暂时只读 | 不自动合并、关闭、打标签、分派 GitHub assignee 或发表评论 |
| D07 | 本地处理可以分派 | 修改平台负责人、进度、优先级、截止时间，不改变 GitHub 原始状态 |
| D08 | 海外服务器与个人域名 | 采用 HTTPS 反向代理、Docker Compose、持久化数据卷 |
| D09 | 单实例部署 | 一个应用进程同时承担 API 和后台任务；不运行多个副本争抢队列 |
| D10 | 未配置集成不能伪装接入成功 | 明确展示演示、未配置、待绑定、发送失败、同步失败等状态 |

### 2.1 暂不纳入首轮范围

- 多组织、多租户、多仓库权限隔离。
- GitHub 组织 / Team 成员资格自动同步。
- 开放注册、加入申请审批、邀请链接注册。
- GitHub 写操作和代用户操作仓库。
- 飞书消息卡片内直接认领、回复、关闭或合并。
- 自动代码评审、AI 自动回复、复杂分派规则引擎。
- Kubernetes、数据库高可用和跨区域多活。

以上能力可以后续扩展，但不作为本次成员管理改造及首次上线的前置要求。

**首要开发增量不是重新开发平台，而是把“环境变量白名单 + 已登录用户列表”升级成“管理员预录入的数据库成员管理体系”。**

## 4. 角色与权限

### 4.1 角色定义

- **管理员（admin）**：管理团队成员、角色、提醒规则和事务分派，查看团队通知与运行状态。
- **普通成员（member）**：查看团队仓库事务，处理自己相关的事项，管理本人的飞书绑定与通知偏好。
- **未授权访问者**：没有成员记录，或成员已停用；不能进入业务页面或读取业务 API。

首轮为单团队工作空间：所有获准成员均可查看该仓库事务，不提供按模块隐藏部分事务的能力。负责模块仅用于筛选和后续路由，不是独立数据权限边界。

### 4.2 权限矩阵

| 操作 | 管理员 | 普通成员 | 未录入 / 已停用 |
| --- | --- | --- | --- |
| GitHub 身份认证 | 允许 | 允许 | 可完成外部认证，但不建立有效平台会话 |
| 查看团队 PR / Issue | 允许 | 允许 | 禁止 |
| 查看个人待办 | 允许 | 允许 | 禁止 |
| 修改任意事务本地字段 | 允许 | 禁止 | 禁止 |
| 修改自己相关事务的进度、优先级、截止时间 | 允许 | 允许 | 禁止 |
| 将未分派事务认领给自己 | 允许 | 允许，需显式认领操作 | 禁止 |
| 将事务分派给其他成员或改派 | 允许 | 禁止 | 禁止 |
| 新增、编辑、停用、启用成员 | 允许 | 禁止 | 禁止 |
| 设置平台角色 | 允许，受最后管理员保护 | 禁止 | 禁止 |
| 管理本人的飞书绑定、偏好 | 允许 | 允许 | 禁止 |
| 替别人完成飞书授权、读取完整 open_id | 禁止 | 禁止 | 禁止 |
| 查看团队通知记录与成员绑定概况 | 允许 | 禁止；只能查看本人通知 | 禁止 |
| 手动同步、修改规则、执行催办 | 允许 | 禁止 | 禁止 |
| 通过平台修改 GitHub 仓库 | 首轮不提供 | 首轮不提供 | 禁止 |

“自己相关”包括平台负责人、GitHub 作者、assignee、个人 requested reviewer；关系必须使用 GitHub 固定 ID 或内部成员 ID 判断。普通成员不得通过修改请求中的 owner 字段绕过权限，未分派事务认领须单独校验，已有其他负责人时不可抢占。

## 5. 成员管理与生命周期

### 5.1 管理员录入的信息

| 字段 | 必填 | 录入 / 获取方式 | 说明 |
| --- | --- | --- | --- |
| GitHub 用户名 | 是 | 管理员输入 | 后台查询真实 GitHub 账号，管理员确认后提交 |
| GitHub 固定用户 ID | 是 | 后台查询获取 | 不允许手填；作为外部身份唯一标识 |
| 团队姓名 / 昵称 | 否 | 管理员输入 | 不因后续 GitHub 昵称更新被覆盖 |
| 负责模块 | 否 | 管理员输入 / 选择 | 例如数据集、模型适配、性能评测；首轮仅用于展示筛选 |
| 平台角色 | 是 | 管理员选择 | 默认普通成员 |
| 管理备注 | 否 | 管理员输入 | 仅管理员可查看 |
| 飞书身份 | 不由管理员录入 | 成员本人授权 | 管理员仅查看已绑定 / 未绑定状态 |

### 5.2 新增成员流程

```text
管理员输入 GitHub 用户名
          ↓
服务端查询 GitHub 用户资料，拒绝组织账号、无效账号
          ↓
展示用户名、头像、主页、固定用户 ID 供管理员确认
          ↓
管理员选择角色并填写团队资料
          ↓
提交时服务端重新验证账号对应关系、检查唯一性
          ↓
创建成员记录：待激活（pending_activation）
          ↓
成员使用相同 GitHub 固定身份首次登录后激活
```

- GitHub 查询失败、超时或限流时，不创建未经核验的成员记录。
- 输入大小写变化、重复提交不能产生重复成员，数据库对 GitHub 固定 ID 设置唯一约束。
- 不依据 GitHub 邮箱、管理员手填姓名或浏览器传入 ID 完成准入。
- 若输入用户名在提交前发生变化，要求重新确认查询结果，不能静默改绑另一账号。
- 预录入成员可以提前成为平台事务负责人；未激活、未绑定时不会发送个人飞书消息，界面必须标识“尚不可达”。

### 5.3 状态模型

| 状态 | 允许登录 | 可接受新分派 | 可接收通知 | 转移规则 |
| --- | --- | --- | --- | --- |
| 待激活 pending_activation | 身份匹配后激活 | 是，标记待激活 | 否 | 首次成功登录 → active |
| 正常 active | 是 | 是 | 还需有效飞书绑定、通知开启和规则满足 | 管理员停用 → disabled |
| 已停用 disabled | 否 | 否 | 否 | 管理员启用后，有首次登录记录 → active，否则 → pending_activation |

不提供普通物理删除，以免破坏分派历史、审计和通知记录。重复添加被停用账号时，应提示进入原记录重新启用，而不是创建新成员。

### 5.4 停用成员的完整效果

在一个数据库事务中完成成员状态更新、会话撤销、该成员待处理 OAuth 状态清理、待发通知取消及审计记录。每次 API 请求和每次消息发送前仍须检查实时状态，不能依赖旧 Cookie 中的角色。

- 已停用成员不能访问或发起新授权；已经打开的页面在下一次 API 请求时失去访问权。
- 不再接收新分派，不再生成或重试个人通知。
- 已有负责人关系保留用于追溯，进入“负责人已停用 / 待重新分派”视图，由管理员批量改派。
- 飞书关联可保留作审计，但视为不可用；重新启用后要求本人重新确认绑定并发送测试消息，才恢复通知。
- 无法召回已经被飞书接受的消息；若停用与正在进行的外部发送恰好并发，应记录这一边界，而非承诺绝对零竞态。

### 5.5 管理员保护与首位管理员

- 首次部署通过受控的一次性引导命令预置首位管理员：服务端解析指定 GitHub 用户名并保存固定 ID，不提供公开初始化网页。
- 首位管理员首次登录后，完成初始化标记；后续重启不得重新应用引导参数覆盖数据库角色。
- 只有至少保留另一位正常且已激活管理员时，才能停用、降级当前管理员；待激活管理员不计作可用的兜底管理员。
- 角色变更和最后管理员检查必须在事务内完成，防止并发操作导致管理员数量归零。
- 紧急恢复使用服务器本地受控命令并记录审计，不开放绕过 GitHub 的万能密码或公开后门。

## 6. GitHub 登录与准入

### 6.1 登录时序

```text
浏览器 → 平台：点击“使用 GitHub 登录”
平台 → 浏览器：生成一次性 state，绑定浏览器 Cookie，跳转 GitHub
GitHub → 平台回调：code + state
平台 → GitHub：服务端换取 Token，查询当前真实用户
平台 → 成员库：按 github_user_id 查询预录入成员
  ├─ 未找到：拒绝访问，不自动创建成员
  ├─ disabled：拒绝访问，不激活、不自动恢复
  ├─ pending_activation：事务性激活并保存首次登录时间
  └─ active：更新展示资料与最后登录时间
平台 → 浏览器：轮换平台会话，进入工作台
```

OAuth 状态应短期有效、单次消费、绑定发起浏览器；GitHub 登录 Token 仅用于当前身份确认，不作为仓库写权限凭证，不写入日志或前端存储。

### 6.2 改名与账号替换

- 成员修改 GitHub 用户名后，固定 ID 不变：允许正常登录，更新用户名快照、头像和主页展示。
- 原用户名被另一 GitHub 账号占用时，固定 ID 不同：不能继承原成员的权限、飞书绑定和待办。
- 管理员不能通过普通资料编辑更换成员的 GitHub 固定 ID。如需换人，停用旧成员并新建记录、显式迁移负责人。

### 6.3 权限边界

平台成员资格与 GitHub repository collaborator / organization membership 不自动等价。管理员把某人录入平台，只代表赋予平台访问权；不会授予此人在 GitHub 上评审、合并、关闭或读取私有仓库的权限。

如未来接入私有仓库，需额外确认平台的数据共享政策：服务器同步凭证能读取的内容，不应在管理员不知情时分享给平台全部成员。

## 7. 个人飞书绑定

### 7.1 绑定流程

1. 正常成员登录后进入个人设置，点击“绑定飞书”。
2. 平台生成短期单次 state，同时记录当前内部成员 ID 和会话关联。
3. 用户在飞书授权页确认身份，回调由服务端换取用户身份信息。
4. 平台再次检查当前成员正常、回调 state 有效且仍属于发起者，防止中途切换 GitHub 账号。
5. 获取当前飞书应用作用域内的真实 open_id，检查是否已经绑定其他成员。
6. 原子保存关联，前端仅显示已绑定、必要的脱敏信息和绑定时间，不返回完整 open_id。
7. 用户主动发送测试消息，确认机器人权限和应用可见范围有效。

不提供“输入别人的飞书 ID 就完成绑定”的入口。一个成员最多一个当前有效绑定，同一飞书应用下一个 open_id 最多属于一个成员。

### 7.2 飞书应用约束

- 采用企业自建应用，开启机器人和应用身份发送个人消息权限。
- 使用者须处于应用可用范围，所需权限由租户管理员审批并发布应用版本。
- GitHub 登录成功，不代表当前用户一定具备该飞书应用的授权资格。
- open_id 具有应用作用域，不能视为跨应用通用个人 ID；更换 App ID 需要重新绑定。
- 不保存长期飞书用户 Token；消息发送使用服务端应用身份凭证。
- 飞书绑定不授予任何 GitHub 写权限。

### 7.3 解绑、重绑与偏好

- 用户可以解绑；解绑立即取消自己的待发通知，不影响 GitHub 登录和既有事务负责人。
- 重新绑定时必须重新完成授权和唯一性检查；不能沿用旧通知中的接收地址。
- 通知开关和免打扰由本人配置，时区首轮固定为 Asia/Shanghai，在页面明确展示。
- 免打扰支持跨午夜；开始、结束同时留空表示关闭，不能只填一端；两端相同按未启用处理并提示。
- 管理员只能查看是否绑定、是否启用通知等运营状态，不代用户完成授权。

## 8. PR / Issue 事务模型与处理闭环

### 8.1 双状态模型

| 类别 | 来源 | 示例 | 平台是否可直接修改 |
| --- | --- | --- | --- |
| GitHub 原始状态 | GitHub API / Webhook | open、closed、merged、draft、CI 状态 | 否 |
| 平台处理状态 | 平台数据库 | todo、in_progress、blocked、done | 是，按角色和参与关系授权 |
| 平台管理字段 | 平台数据库 | owner、priority、due_at | 是，分派受管理员权限约束 |

平台工作流默认：

```text
todo（待处理） → in_progress（处理中） → done（处理完成）
                     ↕                       ↓
                 blocked（阻塞）        需要时显式重新打开
```

本地 done 不等于 GitHub closed / merged；页面并排展示两种状态。例如 Issue 在 GitHub 仍 open、平台已 done，应可筛选，不自动关闭 Issue。

GitHub 关闭或合并时，停止该事务的超期催办，保留本地历史状态；GitHub 重新打开而本地仍 done 时，标记“需复核”，由管理员或相关成员决定是否重开本地流程，避免继续静默忽略。

### 8.2 事务处理链路

```text
新事务进入 → 识别已有责任关系 → 无负责人则进入待分派
   ↓
管理员分派 / 成员认领 → 设置优先级和截止时间
   ↓
负责人处理、评审或与贡献者沟通 → 必要时标记阻塞
   ↓
在 GitHub 完成实际代码或 Issue 操作
   ↓
平台同步 GitHub 状态 → 更新本地进度 → 停止无效催办并保留记录
```

没有自动分派规则时，不凭标签猜测负责人；首轮提供人工分派、普通成员自认领与管理员通知兜底。

### 8.3 个人待办与团队异常视图

- 个人待办：与本人有固定身份关系、GitHub 尚未关闭且本地未完成的事务。
- “与我相关”历史列表：可包含已完成或已关闭事项，与待办计数分开展示。
- 待分派：没有平台负责人，管理员可批量分派。
- 超期：存在截止时间且已到期，或没有截止时间且 GitHub 长时间未更新。
- 责任异常：负责人已停用、待激活或未绑定飞书；不能把“不可达”误显示成“已通知”。

## 9. GitHub 同步与事件接入

### 9.1 接入组成

- **OAuth App**：只负责平台登录身份验证。
- **服务端只读凭证**：负责读取目标仓库 Issue、PR、评审人、Checks / Commit statuses；与个人登录 Token 分离。
- **Webhook**：提供事件触发，需要目标仓库管理员配置。
- **轮询同步**：在 Webhook 缺失或状态遗漏时更新仓库快照；不宣称补齐所有历史评论事件。

公开仓库可匿名读取，但正式部署推荐配置权限合适的只读凭证并关注 API 配额。采用 PAT 还是 GitHub App，需根据目标仓库归属、组织批准策略和权限可用性选择，不能假设平台源码仓库的凭证天然可访问目标仓库。

### 9.2 事件接收与处理

1. 校验请求大小、原始请求体 HMAC-SHA256 签名、目标仓库与事件标识。
2. 按 delivery ID 去重，持久化到收件箱后快速返回 202，不等待完整 GitHub 同步或飞书发送。
3. 后台提取已接受事件批次，获取接收后开始的新快照；同一批次共享一次同步，避免事件风暴重复扫描仓库。
4. 按事件类型识别事务和责任人，事务性写入处理结果与通知任务。
5. 标记事件完成；网络、限流等暂时失败退避重试，不因一次失败丢弃事件。
6. 后台轮询兜底并提供最近成功时间、错误和积压提示。

同步必须完整处理分页，包括 GitHub 返回的 numeric repository canonical 链接，同时拒绝跨域、跨资源和中途更换仓库 ID 的分页跳转。同步失败不得发布半套快照，也不得覆盖本地负责人和工作流字段。

### 9.3 限流与状态新鲜度

首轮保留全量同步能力；后续采用增量读取、定期全量对账、ETag 等优化时，要覆盖关闭、重新打开和更新边界。

- 已开始于事件接收之前的同步不能直接作为该事件已处理的依据。
- GitHub 限流时按响应信息退避，展示“数据可能过期”，保留已有数据，不伪造同步成功。
- CI 无权限或未知时显示 unknown，不推断成成功。
- 目标规模先以现有仓库量级验收，不作未压测的吞吐保证。

## 10. 通知与催办设计

### 10.1 触发规则

| 类型 | 首轮处理 | 主要接收对象 |
| --- | --- | --- |
| 新增 Issue / PR | Webhook 事件提醒 | 已录入的相关成员；无人承接则管理员兜底 |
| 被分派或请求评审 | 事件提醒 | 对应责任人 / 个人评审人 |
| 新评论、评审意见 | 事件提醒 | 相关负责人、作者、评审人；跳过事件发起者 |
| 平台分派 / 改派 | 目标增量：生成本地分派事件 | 新负责人；未激活 / 未绑定则标记不可达 |
| 截止时间超期 | 定时催办 | 当前负责人及相关成员 |
| 长期未更新 | 定时催办 | 当前负责人及相关成员 |
| CI 失败、合并冲突 | 首轮展示，不承诺即时通知 | 后续扩展需明确事件与分支 / PR 关联 |
| GitHub 关闭 / 合并 | 同步状态并停止催办 | 首轮不强制发送完成通知 |

默认静默阈值 48 小时、超期提醒冷却 24 小时。无明确截止时间时，以 GitHub 更新时间判断静默；修改本地优先级不自动重置 GitHub 静默时间。管理员可显式调整截止时间，不能把“静默”误解成已确认的人工响应 SLA。

### 10.2 接收人解析顺序

1. 根据固定 ID 匹配平台负责人、GitHub 作者、assignee、个人 requested reviewer。
2. 去除重复成员、已停用成员和事件发起者；按权限、绑定和个人偏好决定是否发送。
3. 没有可承担责任的正常内部成员时，路由给正常管理员，并在管理台标记待分派。
4. 有明确负责人但其未激活 / 未绑定时，保留负责人，不把任务悄悄转给别人；管理员看到“负责人不可达”，后续可选择单独的运营告警策略。
5. 所有管理员均不可达时，产生可见的未投递原因和运营告警，不能将结果显示为成功。

通知是否可达不改变事务归属。管理员兜底不等于管理员自动成为平台负责人。

### 10.3 队列、去重与失败恢复

- 事件通知唯一键：仓库 + delivery ID / 本地事件 ID + 接收成员 ID。
- 超期催办唯一性：每条事务、每个接收成员最多一个 pending / sending 的同类催办。
- 冷却从上次成功发送时间计算，不从入队时间计算，避免免打扰后集中补发多条催办。
- 发送前重新检查成员状态、绑定版本、接收关系、事务状态、全局规则和个人偏好。
- GitHub 已关闭、本地已完成、接收者被停用或不再相关时，取消过期的待发消息。
- 同一通知的失败重试复用 UUID；暂时失败建议采用可见的退避时间，默认最多 3 次。
- 对明确的绑定失效或权限错误停止自动轰炸，保留脱敏原因，提示用户重新授权或管理员处理应用权限。
- 免打扰仅延期，不增加发送失败次数；保持队列公平，不能让前排免打扰任务长期阻塞其他接收者。
- 无法承诺严格 exactly-once；外部发送结果未知、宕机恢复超出飞书去重窗口时，仍可能重复送达。

### 10.4 消息内容

消息包含仓库、PR / Issue 编号、标题、提醒原因、当前责任 / 截止时间摘要、平台处理入口和 GitHub 原文入口。控制长度，避免在消息中复制完整敏感正文。

首轮使用纯文本消息，不从 GitHub 内容执行模板代码，不把外部评论当作平台指令。点击消息后在网页或 GitHub 完成处理，飞书消息发送成功只代表提醒已投递，不代表事务已处理。

## 11. 数据设计

以下是目标逻辑模型，不是已经执行的数据库变更。新增结构必须采用版本化迁移，不能直接覆盖现有 SQLite 数据。

| 实体 | 核心字段 | 关键约束 / 用途 |
| --- | --- | --- |
| members | id、github_user_id、github_login、display_name、module、role、status、created_by、first_login_at、last_login_at、version、timestamps | 内部 UUID 主键；github_user_id 唯一；准入与角色的唯一业务来源 |
| users / profiles | GitHub 固定 ID、member_id、GitHub 昵称、头像 | 首次登录后生成或关联；member_id 唯一；团队姓名与 GitHub 昵称分开 |
| feishu_bindings | member_id、app_id、open_id、status、bound_at、verified_at、binding_version | member_id 唯一；(app_id, open_id) 唯一；成员停用或换应用后不得直接恢复发送 |
| sessions | token_hash、member_id、csrf、expires_at | 不存明文会话 Token；实时核验成员状态与角色 |
| oauth_states | state_hash、provider、member_id、browser_hash、expires_at | 一次性、短期、区分提供方，飞书关联发起成员 |
| items | id、repository_id、number、kind、GitHub 快照、platform_owner_member_id、workflow、priority、due_at、version | 仓库内编号唯一；负责人引用成员 ID；GitHub 快照与本地字段分离 |
| rules / settings | enabled、stale_hours、cooldown_hours、sync settings | 全局规则默认关闭；配置变更可审计 |
| webhook_inbox | delivery_id、repository_id、event、payload、status、attempts、next_at、received_at、processed_at | delivery_id 唯一；入库后应答；失败可恢复 |
| notifications | id、dedupe_key、item_id、recipient_member_id、binding_version、reason、status、attempts、next_at、sent_at、error_code | 固定成员路由，不依赖可变用户名；唯一去重键 |
| audit_logs | actor_member_id、action、target_type、target_id、before、after、request_id、created_at | 覆盖成员、角色、绑定状态、分派、规则；敏感值不记录 |
| schema_migrations | version、applied_at | 可追踪升级，避免隐式不兼容修改 |

补充约束：

- GitHub 用户 ID 按不丢精度的文本形式存储，禁止依赖前端传入的授权身份。
- 外部 GitHub 参与者即使不属于团队，也保留 ID / 用户名快照以展示上下文，但不因此创建可登录成员。
- 新版本不得仅按用户名关联作者、assignee、reviewer 或通知接收人。
- 首轮保留单仓库运行，结构记录 repository_id 是为了审计和防串库，不代表已经支持多仓库产品。
- 编辑成员、负责人和角色使用 version 做乐观并发控制，冲突返回 409 并提示刷新。

## 12. 接口与页面设计

### 12.1 新增 / 改造接口（目标设计）

所有管理员写接口要求有效会话、实时角色校验、精确 Origin、CSRF Token、输入校验和审计。

| 接口 | 权限 | 作用 |
| --- | --- | --- |
| GET /api/admin/github-users/resolve?login=... | 管理员 | 服务端核验真实 GitHub 个人账号，返回供确认的公开资料；限流 |
| GET /api/admin/members | 管理员 | 按角色、状态、模块、绑定情况分页筛选全部预录入成员 |
| POST /api/admin/members | 管理员 | 核验 GitHub 用户名后创建预录入成员，默认待激活 |
| PATCH /api/admin/members/:id | 管理员 | 修改团队姓名、模块、备注、角色；固定 GitHub 身份不可修改 |
| POST /api/admin/members/:id/disable | 管理员 | 停用、撤销会话、取消待发消息、写审计 |
| POST /api/admin/members/:id/enable | 管理员 | 重新启用，但不绕过飞书重新确认要求 |
| GET /api/assignable-members | 正常成员 | 仅返回可分派成员的必要字段，不含管理备注和飞书身份 |
| POST /api/items/:id/claim | 正常成员 | 原子校验未分派后认领给自己，不允许抢占 |
| PATCH /api/items/:id | 授权相关成员 / 管理员 | 保留事务编辑；负责人改用成员 ID，改派由管理员执行 |
| GET /api/admin/audit-logs | 管理员 | 查询成员 / 分派 / 规则等敏感操作审计 |
| GET /api/admin/integration-status | 管理员 | 查看同步时间、Webhook 积压、通知失败、集成配置状态，不返回密钥 |

既有登录、飞书 OAuth、个人偏好、通知记录和看板接口保留兼容层，逐步迁移。未录入 / 停用成员的登录返回明确但不泄露内部详情的提示；不存在有效会话返回 401，无操作权限返回 403，重复身份或版本冲突返回 409。

### 12.2 页面结构

- **登录页**：GitHub 登录入口，说明仅限管理员已录入的团队成员。
- **工作台**：开放事务、个人待办、超期、待分派、责任异常与同步健康状态。
- **全部事务 / 我的待办**：搜索、GitHub 状态、平台进度、负责人和模块筛选。
- **事务详情**：原始内容、责任关系、双状态、截止时间、修改记录；跳转 GitHub。
- **成员管理（管理员）**：全部预录入成员、待激活 / 正常 / 已停用、新增成员、编辑角色、启停、绑定与可达性概况。
- **提醒规则（管理员）**：总开关、静默阈值、冷却、手动执行、默认关闭提示。
- **通知记录**：成员只见自己的记录，管理员见团队记录，区分待发 / 发送中 / 已发送 / 失败 / 已取消。
- **个人设置**：GitHub 真实身份、飞书授权 / 解绑 / 测试、个人通知开关、明确时区的免打扰设置。
- **运行状态与审计（管理员）**：最近同步、事件积压、失败原因、成员停用与角色变更记录。

## 13. 海外服务器与域名部署

### 13.1 推荐拓扑

```text
团队浏览器 / GitHub Webhook / OAuth 回调
                     ↓ HTTPS
          triage.<个人域名> → DNS → 海外服务器
                     ↓
          宿主机 Caddy 或现有 Nginx（80 / 443）
                     ↓ HTTP，仅本机访问
          127.0.0.1:3210 → Docker 应用单实例
                     ├─ React 静态网页 + Express API
                     ├─ GitHub 同步 / Webhook worker / 提醒 worker
                     └─ SQLite 数据卷（不可随容器重建丢失）

应用出站：GitHub API、GitHub OAuth、飞书 OAuth / 消息接口
```

推荐先使用 Linux LTS 服务器。2 vCPU、2 GB 内存可作为小团队起步的资源规划参考，不是压测后的最低保证；若在服务器上构建镜像，应另外评估构建内存和磁盘空间。

### 13.2 网络与 HTTPS

- 选择专用子域名，不假设现有根域名网站可以被替换。
- 配置 DNS A 记录；只在 IPv6 连通且防火墙配置正确时配置 AAAA，避免部分用户连接失败。
- 防火墙 / 安全组仅开放必要的 80、443；SSH 限制可信来源并使用密钥。
- 3210 端口仅绑定宿主回环地址，SQLite 无对外监听端口。
- 推荐宿主机 Caddy 自动管理证书；若已有 Nginx，应复用既有入口，不并行争抢 80 / 443。
- 海外服务器不自动保证中国境内用户访问体验，应实测团队所在地网络、GitHub 跳转和飞书回调。

宿主机 Caddy 示例（域名必须替换）：

```caddyfile
triage.example.com {
    reverse_proxy 127.0.0.1:3210
}
```

此示例中的 Caddy 运行在宿主机。如果将 Caddy 也容器化，应改用 Docker 网络中的应用服务名和端口，不能把代理容器内的 127.0.0.1 当成应用容器。

### 13.3 回调地址与外部配置

以下以示例域名说明，不是已分配的真实域名：

| 配置项 | 示例 |
| --- | --- |
| BASE_URL | https://triage.example.com |
| GitHub OAuth callback | https://triage.example.com/auth/github/callback |
| 飞书 OAuth redirect URI | https://triage.example.com/auth/feishu/callback |
| GitHub Webhook payload URL | https://triage.example.com/api/webhooks/github |

BASE_URL 必须等于用户实际访问的源，不带业务子路径。生产与测试使用不同应用配置、回调、密钥及数据库，不能在正式域名启用自动登录的演示模式。

平台源码为私有仓库时，服务器拉取代码使用仅能读取源码仓库的 deploy key 或适当的只读凭证；这与业务仓库的同步凭证是两套权限，不能混用个人高权限 Token。

### 13.4 上线顺序

1. 核实服务器系统、资源、Docker、当前网站和端口占用，不修改已有服务前先明确冲突。
2. 配置子域名、HTTPS、持久化卷和只读源码获取方式。
3. 在隔离测试环境配置正式模式，禁止演示模式与真实数据共库。
4. 配置 GitHub OAuth、同步凭证、飞书应用和回调；通过一次性引导创建管理员。
5. 实测管理员登录，预录入一名测试成员，验证未录入账号被拒绝。
6. 完成真实飞书绑定与测试消息，核对应用范围和授权。
7. 在具备目标仓库管理权限时注册 Webhook；否则明确启用“仅轮询”降级模式。
8. 完成首次导入，核对事务数量、负责人映射和数据新鲜度，不发送历史事件消息。
9. 执行备份 / 恢复演练，再由管理员开启提醒。
10. 扩大到团队使用，观察通知量与 API 配额后调整参数。

## 14. 安全、审计与运维

### 14.1 安全控制

- Cookie 使用 HttpOnly、SameSite=Lax，HTTPS 下启用 Secure；不把授权 Token 存入 localStorage。
- OAuth state 单次、短期、绑定浏览器；飞书绑定附加绑定当前成员身份。
- 所有角色、成员状态、分派权限在后端校验；禁用后已有会话不能继续使用。
- Webhook 校验原始请求签名，不能先解析后重新序列化签名内容。
- 凭证通过服务器受限配置 / secret 注入，不提交 Git，不出现在前端或日志中。
- GitHub 内容是外部不可信文本，不执行脚本，不将描述或评论当作后台指令。
- 前置代理终止 TLS 后，可信源以配置 BASE_URL 为准；不得信任任意 Host / Forwarded 头。
- 代理后的限流只信任明确的代理链，避免所有用户共用一个错误 IP 限额或任意伪造来源 IP。
- 日志去除 code、Token、完整 open_id、Cookie 和原始敏感正文；记录 request ID 以便排障。
- 海外存储涉及团队成员身份及仓库内容，应由团队确认组织的数据存储、跨境与保留要求，不预先假定合规性。

### 14.2 备份与恢复

- 提议初始目标：每天至少一次一致性备份，RPO 不超过 24 小时；RTO 4 小时作为运维目标，需演练确认，不视为已达成承诺。
- 优先使用 SQLite 在线备份机制；简单方案可停应用后备份完整数据目录，不只复制运行中的单个 SQLite 主文件。
- 备份至少一份放在服务器之外，限制访问并加密；密钥与备份分开管理。
- 建议每日备份保留 7 天、周备份保留 4 周，最终由团队确定容量与合规要求。
- 恢复同时考虑数据库版本、应用镜像版本和重复通知：恢复验证期间关闭发送器，再核对已发送记录与上游去重窗口。
- 发布前备份，镜像按提交 SHA / 版本固定；涉及数据迁移时，不能只换回旧镜像而不核对 schema 兼容性。

### 14.3 可观测性与数据保留

- 健康检查区分“进程可响应”与“集成正常”；健康接口不泄露密钥和团队数据。
- 关注最近成功同步时间、GitHub 限流、事件积压、最老待发消息、消息失败率、磁盘、SQLite/WAL 增长和证书有效期。
- 监控告警渠道应独立于本平台个人飞书绑定，避免飞书集成本身失效时没有人知道。
- 建议事件原始载荷保留 30 天，通知与业务审计保留 180 天，日志轮转；均为待确认参数，并为尚未处理的任务设置例外，不能清理掉待重试事件。
- 对已接收但长期失败的事件提供管理员可见状态和人工重试，不能无限积压而无提示。

## 15. 现有初版迁移方案

### 15.1 迁移步骤

1. 备份正式数据库及配置，在副本上演练，记录 schema 版本。
2. 创建 members、绑定关系、审计、版本号等目标结构。
3. 读取原管理员 / 成员白名单，通过 GitHub API 核验账号并解析固定 ID；外部核验在数据库写事务之外完成，避免持锁等待网络。
4. 已登录用户按其已保存的 GitHub 固定 ID 关联 members；尚未登录的有效白名单账号创建待激活成员。
5. 原 users 中的团队显示资料、飞书关联和偏好迁入对应身份；无法确认一致性的关联暂停发送并要求重新授权。
6. 原 owner、通知 recipient 等用户名引用解析为 member_id；无法唯一确认的记录标为待人工处理，绝不按模糊匹配转给其他人。
7. 补齐 GitHub 作者 / assignee / reviewer 的固定 ID 快照，停止按用户名授权。
8. 撤销旧会话，切换准入、角色、发送检查至数据库来源；环境白名单不再覆盖网页管理结果。
9. 完成管理员、普通成员、未激活、停用、GitHub 改名、飞书重绑和回滚验证，再开放团队使用。

### 15.2 迁移失败与回退

GitHub 限流、账号不存在、身份冲突或无可用管理员时，迁移不得悄悄放宽访问。输出脱敏待处理清单并停止切换；保持旧系统或回退到备份，由管理员确认后重试。

演示数据库与正式数据库分开迁移；不能把 demo-maintainer 等模拟身份导入正式成员库。迁移脚本应幂等，重跑不重复创建成员或覆盖管理员后续编辑。

## 16. 验收标准

以下是目标版本验收项，不是已经完成的测试清单。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 管理员新增成员 | 输入真实 GitHub 个人账号并确认，保存固定 ID、角色和待激活状态 |
| A02 | 非法或重复录入 | 不存在、组织账号、重复固定 ID 被拒绝；无半条成员记录 |
| A03 | 首次登录激活 | 预录入成员用匹配的 GitHub 身份登录，激活原记录，不产生重复账号 |
| A04 | 陌生账号访问 | 即使 GitHub OAuth 成功，也不能读取业务数据或自动加入团队 |
| A05 | GitHub 改名 / 用户名复用 | 原固定 ID 可继续登录；占用旧用户名的新 ID 无法继承权限 |
| A06 | 成员停用 | 下一次请求失去权限、会话撤销、待发消息取消、不可再分派；历史可追溯 |
| A07 | 管理员保护 | 最后一个正常管理员无法被停用 / 降级；并发操作也不能绕过 |
| A08 | 飞书本人绑定 | 中途切换平台账号、state 重放、跨成员重复 open_id 均被拒绝 |
| A09 | 预分派与认领 | 可分派给待激活成员并展示不可达；普通成员只能原子认领未分派事务 |
| A10 | 权限隔离 | 普通成员不能操作成员接口、改派他人或查看团队通知；伪造请求无效 |
| A11 | 双状态与关闭 | 本地 done 不回写 GitHub；GitHub 关闭后不再催办；重新打开标记需复核 |
| A12 | Webhook 可靠性 | 签名无效被拒绝；重复 delivery 不重复生成通知；持久化后快速应答，重启可恢复 |
| A13 | 快照与限流 | 事件不被接收前的旧同步吞掉；批次共享同步；限流时保留数据并显示过期 |
| A14 | 通知去重与免打扰 | 跨午夜有效；积压超过冷却仍只有一条同类催办；发送后才开始新冷却 |
| A15 | 发送结果真实 | 未绑定、停用、应用无权限、网络失败不能显示已送达；发送失败可追溯 |
| A16 | 实际部署 | 域名 HTTPS 正常，3210 不向公网开放，容器重建数据保留，无演示自动登录 |
| A17 | 外部集成联调 | 真实 GitHub 登录、Webhook、飞书授权和个人收信均有目标环境验收记录 |
| A18 | 运维恢复 | 在隔离环境成功恢复备份，核对角色、绑定、事务、队列并避免误补发 |
| A19 | 移动端与桌面 | 主要页面可用、无文档级横向溢出，错误状态清晰，键盘能关闭详情抽屉 |

性能与时效先作为验收目标测量：正常资源条件下，Webhook 持久化应答争取在 2 秒内；事件 worker 目标轮询间隔 15 秒，但消息到达时间还受 GitHub 同步、限流、免打扰和飞书服务影响，不承诺“所有通知 15 秒内送达”。

## 17. 分阶段实施计划

| 阶段 | 工作 | 交付 / 出口条件 |
| --- | --- | --- |
| P0：设计确认 | 确认角色、成员字段、可见性、默认参数与部署约束 | 本设计稿确认，待确认项有负责人 |
| P1：成员体系改造 | 数据迁移、首管理员引导、管理员 CRUD、固定 ID 登录准入、停用联动、角色保护 | A01–A07、A10 与迁移回归通过 |
| P2：责任与通知完善 | 固定 ID 分派 / 路由、预分派、原子认领、不可达提示、管理员兜底、通知与审计 | A08–A15 通过，保留已有集成测试 |
| P3：海外部署 | 服务器与域名、HTTPS、容器、密钥、真实回调、备份监控 | A16–A19 通过，完成恢复演练 |
| P4：小范围试运行 | 管理员和少量成员先用，观察通知噪声、积压、配额与访问速度 | 修复试运行问题后扩大到团队 |

## 18. 待确认信息

不阻塞本设计文档，但实施前需要明确：

1. 服务器系统、CPU / 内存 / 磁盘、Docker 状态，以及已有网站、反向代理、80 / 443 占用情况。
2. 域名与 DNS 管理方、拟用子域名、团队主要访问地区。
3. 首位管理员及首批成员的 GitHub 用户名；不要在设计稿中填入密码或私钥。
4. 是否具备 AISBench/benchmark 的 Webhook 管理权限；若没有，接受哪些“仅轮询”降级限制。
5. 飞书企业租户、自建应用创建与发布权限、成员是否可纳入应用范围；使用飞书还是 Lark 需确认，不能直接假定 API 域名兼容。
6. 全员可见单仓库事务的权限模型是否符合团队预期；若未来是私有仓库，需重新审查共享范围。
7. 默认静默 / 冷却 / 时区、管理员兜底接收策略、数据保留和备份目标。
8. 是否接受待激活成员可提前被分派，但未绑定前无法接收个人飞书提醒。

**设计结论：采用管理员维护的成员名单作为准入和角色来源，GitHub OAuth 作为唯一登录身份认证，飞书 OAuth 作为个人通知身份关联，在既有初版上增量改造，并以海外服务器上的单实例 HTTPS 部署完成团队试运行。**
