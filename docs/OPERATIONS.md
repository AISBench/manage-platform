# v0.3 部署与运维清单

本文提供操作方案，不表示服务器已被连接或配置。上线前需要真实服务器、域名、GitHub 和飞书应用配置，以及目标仓库 Webhook 管理权限。

## v0.3 游客、注册与升级注意事项

- 根路径 `/` 是游客门户，成员工作区为 `/workspace`；GitHub OAuth callback 地址不变。GitHub 验证不是成员准入，未知身份只能显式申请，审核通过后必须重新登录。
- 首位管理员仍通过服务器本地 bootstrap 创建，不能让第一个注册者自动成为管理员；已有管理员与成员不需要重新审核。
- 真实环境公开数据默认关闭。管理员进入“访问策略”，确认目标仓库为 public 后启用，再手动完整同步生成公开投影。开启开关后出现 no_snapshot 是正常状态，不能用内部数据回填游客页面。
- 公开性有效期 60 秒；后台刷新失败或过期时公开接口失败关闭，已批准成员仍可使用内部数据。请配置适当的 GitHub 只读凭证，避免匿名 API 配额不足导致公开门户频繁不可用。
- 注册默认接受申请，拒绝后默认 24 小时冷却，待审核容量默认 1000；这两项和公开开关在网页数据库策略中管理，不是环境变量白名单。关闭注册不影响已批准成员。
- 游客、申请和成员是不同作用域。测试匿名窗口不应收到成员 Cookie、不应出现个人中心；受限申请者不能访问飞书或成员 API；公开反馈不能夹带管理员内部备注。
- 从 v0.2 升级：先在线备份，停止旧实例，构建新镜像并启动，schema3 自动增量迁移。不要重复 bootstrap 或导入旧白名单。旧镜像不能直接读写 schema3，回退应恢复匹配备份。
- 申请说明和审核历史会保留，当前不自动清理申请记录；上线前需确认团队的数据保留与隐私要求。定时清理只会删除已过期的受限会话等既定对象。
- 演示现在也是游客先进入，管理体验必须显式点“演示管理员登录”。这不是线上身份认证入口，正式模式不提供模拟登录 API。

```bash
# 新版镜像构建完成后，先对原数据卷做一致性备份；备份文件须是新文件。
docker compose build
docker compose run --rm platform node server/cli.js backup --output /app/data/backups/pre-v03.sqlite
docker compose stop platform
docker compose up -d
```

上述步骤适用于已有 v0.2 数据库；全新部署使用下方初始化流程。不要执行带 `-v` 的 down 命令删除数据库卷，也不要同时运行新旧实例写同一卷。

## 1. 上线前核查

- 确认服务器系统、CPU / 内存 / 磁盘、Docker 版本、已有网站及 80 / 443 端口占用。不要直接替换既有反向代理。
- 专用子域名 A 记录指向服务器；仅在 IPv6 已验证时配置 AAAA。
- 安全组开放 80 / 443；SSH 使用密钥并限制来源。3210 不向公网直接开放。
- 宿主机 Caddy / 现有 Nginx 提供 HTTPS；应用容器只经宿主回环入口访问。应用 [Compose 配置](../compose.yaml) 已限定该端口绑定。
- 平台私有源码使用只读 deploy key；业务仓库读取凭证独立配置。凭证不能放在 Git remote URL、网页、截图或日志中。
- 使用非演示配置，BASE_URL 精确等于外部 HTTPS 源。确认生产与演示使用不同数据库。
- 检查服务器到 GitHub 和飞书的出站连接，以及团队所在地访问速度。海外位置不自动保证连通性。

## 2. 新装启动

按 [环境模板](../.env.example) 填写 `.env` 并限制文件访问权限。若已有数据库，先判断是否需要旧版迁移，不要直接 bootstrap。

```bash
docker compose build
docker compose run --rm platform node server/cli.js bootstrap --github YOUR_GITHUB_LOGIN
docker compose up -d
docker compose logs --tail=100 platform
```

首管理员通过受控本地命令预置 GitHub 固定 ID，首次 OAuth 登录激活。不存在公开初始化接口或万能密码。若命令提示失败，核查数据库路径、GitHub 个人身份、连接、重复初始化与权限，不要打印真实密钥。

HTTPS 可参考 [宿主机 Caddy 样例](../deploy/Caddyfile.example)。Caddy 容器化时应使用 Docker 服务名访问平台，不能沿用容器自己的 127.0.0.1。

反向代理后需根据实际代理链配置 TRUST_PROXY 的明确地址 / 子网，避免所有团队用户错误共享一个限流 IP。默认不信任代理；不使用 true、任意跳数或无约束来源。Docker 网络网关地址以服务器实际值为准，不能照抄示例。

## 3. 真实集成验收

1. GitHub OAuth 回调为 `BASE_URL/auth/github/callback`。管理员正常登录，陌生账号不被自动注册。
2. 网页核验并预录入测试成员，成员首次登录激活。测试改名仍按固定 ID 识别。
3. 仓库同步使用只读服务器凭证；先手动同步，核对开放 / 关闭事务与 PR CI。
4. Webhook 回调为 `BASE_URL/api/webhooks/github`，配置随机 secret；观察 GitHub 投递与平台收件箱，验签失败必须拒绝。
5. 飞书自建应用发布、机器人和个人消息权限完成审批、测试成员纳入应用范围；回调为 `BASE_URL/auth/feishu/callback`。
6. 成员本人绑定后发送测试消息。界面变为已验证、本人实际收到消息，才算通知通道验收成功。
7. 确认初次同步不发送历史事件消息，规则仍默认关闭。
8. 执行备份及隔离恢复演练，再由管理员启用提醒，先小范围试运行。

无 Webhook 管理权限时，明确告知团队只使用轮询、平台分派和超期提醒，不宣称完整即时事件提醒。

## 4. v0.1 升级

先在副本演练，安排短维护窗口。保持旧环境白名单输入，使用同一持久化数据卷。

```bash
# 已运行的旧实例也可在线备份；备份命令使用新版本CLI时需先构建新镜像。
docker compose build
docker compose run --rm platform node server/cli.js backup --output /app/data/backups/pre-v02.sqlite
# 在 .env 中保留旧 ADMIN_GITHUB_LOGINS 与 ALLOWED_GITHUB_LOGINS。
# 停止旧实例，防止旧代码继续按用户名写入。
docker compose stop platform
docker compose run --rm platform node server/cli.js migrate-members
docker compose up -d
```

迁移核验失败时不切换，也不新建一个宽权限白名单绕过；检查用户名复用、ID 冲突、限流和演示数据混入。核验通过后，数据库成为唯一准入 / 角色来源，环境白名单不再授权。旧会话撤销，旧待发消息取消；飞书绑定必须重新由本人测试。

如需回滚，先关闭提醒并停止新实例，保护当前数据库副本，然后恢复升级前的一致性备份和匹配旧镜像。不要让 v0.1 与 v0.2 同时读写同一数据库。

## 5. 备份与恢复

应用提供 SQLite 在线一致性备份，包含已提交 WAL 内容，目标必须是新文件：

```bash
docker compose exec platform node server/cli.js backup --output /app/data/backups/platform-20261111.sqlite
```

- 文件名应按每次备份时间生成，不覆盖既有备份。样例日期仅为示意。
- 备份含团队身份、事务和绑定信息，需加密并至少存一份到服务器之外；数据卷内副本不算异地备份。
- 每日备份与保留策略由部署者在服务器运维系统中显式配置；本次代码不会自动安装 cron 或修改服务器任务。
- 恢复必须使用隔离数据库和环境，先关闭提醒与出站发送；核对成员 / 角色、事务、迁移版本、队列与日志，再决定正式切换。
- 受制于飞书上游去重窗口，恢复旧备份可能重新出现已投递任务；不能盲目启用发送器，也不能承诺严格 exactly-once。
- 建议目标 RPO 24 小时、RTO 4 小时，必须经过实际恢复演练才可作为运营承诺。

## 6. 观察与排障

| 现象 | 检查点 |
| --- | --- |
| 成员 GitHub 登录后被拒绝 | 数据库中是否预录入正确固定 ID、是否停用；运行时修改环境白名单无效 |
| 无法停用 / 降级管理员 | 是否最后一位正常且已激活管理员；待激活管理员不能作为兜底 |
| 成员无法接收飞书 | 是否本人绑定当前 App ID、是否测试确认、通知开关 / 免打扰、成员状态、应用发布 / 可用范围 / 权限 |
| 已启用成员仍不可达 | 停用保留关联但撤销验证，需要本人重新测试；换 App ID 需要重新绑定 |
| 绑定或测试冲突 | 期间发生解绑、重绑、会话切换或停用；旧操作被拒绝是保护机制，重新发起当前操作 |
| 提醒显示取消但有送达审计 | 外部服务已接受请求时权限恰好撤销，无法召回；查看 DELIVERED_AFTER_REVOCATION，而不是重试 |
| 同步长时间未更新 | GitHub 连接、只读权限、限流退避时间、进程 / 磁盘状态；保留旧数据不代表同步成功 |
| Webhook 积压 | 签名 / 仓库、最近同步、限流、最老待处理时间；用管理员重试接口重置待处理事件，不重放已完成事件 |
| 保存返回409 | 页面版本已过期或业务冲突；刷新并重新确认，不覆盖别人的修改 |

管理员“运行状态”展示最近同步、退避、队列和成员状态；“操作审计”追溯变更。`/api/health` 只代表应用能响应，不代表 GitHub / 飞书已联通。

默认清理已完成事件 30 天、终态通知及审计 180 天；pending / sending 任务不因保留期被删除。配置为 EVENT_RETENTION_DAYS 和 RECORD_RETENTION_DAYS。不要将长期待重试任务当成正常状态，需外部监控提醒运营者。

## 7. 安全恢复管理权

只有拥有服务器本地权限、确认确需恢复时执行：

```bash
docker compose exec platform node server/cli.js recover-admin --github YOUR_GITHUB_LOGIN
```

命令重新核验 GitHub 个人身份并记录审计，不提供密码登录。恢复已停用身份不会恢复旧飞书验证。日常角色管理应使用网页，不应把恢复命令当作每次启动脚本。

## 8. 尚未替部署者完成的事项

实际服务器配置、DNS / TLS、GitHub OAuth App 和 Webhook 注册、飞书租户审批 / 发布、真实个人收信、Docker 目标环境运行、独立监控告警、异地备份和恢复演练均需在真实环境执行。本说明不包含任何真实密码、Token、SSH 私钥或正式域名。
