# GitHub 注册审核与游客模式设计

- 文档版本：v1.0（在原平台设计上的变更设计）
- 状态：已按本设计实现 v0.3；代码验证与真实环境边界见 [验证记录](VALIDATION-V03.md)
- 适用基线：AISBench Triage v0.2
- 目标仓库：[AISBench/benchmark](https://github.com/AISBench/benchmark)
- 原设计：[平台设计文档](DESIGN.md)

> 新的访问路径：**游客直接看公开仓库概况；用户通过 GitHub 验证身份并提交加入申请；管理员审核通过后，用户才能登录成员工作区、使用个人中心和绑定飞书。**
>
> 本文替代原设计中“不开放注册”“匿名访客不能看事务概况”的约束，其他固定身份、成员停用、飞书本人授权和最小权限原则继续有效。后续已完成 v0.3 代码、迁移与本地验证；并未执行海外正式部署或替代真实 GitHub / 飞书授权验收。

## 1. 产品定位与关键决策

平台分为三个入口层次：

1. **公开门户**：无需登录，查看公开的 PR / Issue 总体情况。
2. **申请入口**：GitHub 验证身份后申请加入，审核期间只查看自己的申请状态。
3. **成员工作区**：白名单审核通过且成员未停用，才能进入个人和协作功能。

不新增用户名密码、邮箱密码注册，也不让用户把 GitHub 密码交给平台。注册按钮跳转 GitHub 官方 OAuth 授权页，回调服务器获取真实身份，平台仅创建本平台的申请 / 成员记录。

### 已确定的方向与推荐细则

- 用户提出：支持 GitHub 注册申请、管理员审核白名单、通过后登录，以及无个人中心的游客模式。
- 本设计推荐：审核前不可绑定飞书；审核通过默认普通成员；游客只看 GitHub 公开数据，不看团队内部工作流；现有管理员预录入入口保留。
- 重申请冷却、申请字段和公开统计范围等参数是推荐值，实施前仍可调整。

| 使用 GitHub 提交加入申请 | 可发起 | 待审核不重复提交；被拒绝按规则重申请 | 无需申请 | 无需申请 |
| 查看本人申请状态和公开审核反馈 | GitHub 验证后 | 是 | 可显示已通过 | 可查看团队申请 |

| 查看团队成员、审核队列和内部审核备注 | 否 | 否 | 否 | 是 |

**“申请状态页”是受限页面，不是个人中心。游客模式也不是现有演示管理员模式，不能自动登录管理员、复用管理员权限或访问团队 API。**

## 3. 游客模式

### 3.1 首页布局

```text
顶部：AISBench 协作平台        [GitHub 登录] [申请加入]

[开放 PR 数] [开放 Issue 数] [已关闭 PR 数] [已关闭 Issue 数]

公开事务列表：
类型 / 编号 / 标题 / GitHub状态 / 标签 / GitHub更新时间 / 原文入口

页脚：数据更新于……；来自 GitHub 公开仓库
```

不显示个人头像菜单、“我的任务”“个人中心”“飞书绑定”“通知记录”“成员管理”和管理功能。可用单个“使用 GitHub 登录 / 申请加入”按钮，回调后根据真实状态分流，避免重复授权。

### 3.2 数据公开边界

游客初版允许的字段：仓库名称 / GitHub 链接，事务类型、编号、标题、GitHub open / closed 状态、公开标签、GitHub 公开作者用户名、创建 / 更新时间和原文链接。合并状态仅在来源明确时展示，不能把全部 closed PR 当作 merged。

推荐首版只展示摘要，不展示完整正文、评论或 diff；有进一步需求时再扩展。统计采用相同公开快照口径，明确 PR 与 Issue 分开计数，因为 GitHub issues 接口也包含 PR。

以下信息即使是“总体统计”，也不能直接公开：

- 平台负责人、内部成员 ID、真实姓名、负责模块、成员状态或飞书可达性。
- 平台 todo / in_progress / blocked / done、优先级、截止时间、超期数、责任异常数、个人工作量。
- 本地活动、审计、内部备注、申请名单、审核意见、通知记录和失败原因。
- 完整飞书 ID、授权凭证、Webhook 载荷、内部运行状态和基础设施详情。

公开序列化器必须采用**允许字段清单**，不能将当前成员 Item 对象整体返回后依赖前端隐藏列。公开查询也不能按内部负责人、模块、优先级等字段筛选，防止通过总数或搜索结果间接泄露内部信息。

### 3.3 仓库公开性与缓存

- 游客数据默认仅用于明确验证为 public 的业务仓库。服务器持有能读私有内容的 Token，并不代表这些内容可以公开。
- 新部署先关闭公开门户数据开关；配置时核验仓库公开性，启用后正常首页即为游客概览。管理员关闭公开开关不影响已批准成员的内部访问。
- 生成公开快照时，核验 GitHub 仓库 ID / 公开性，从本次完整公开同步结果生成独立字段投影，原子替换；不能从可能混入私有历史的内部表无限合并后对外展示。
- 为公开快照保存仓库 ID、生成批次、数据时间、公开性核验时间。公开性建议每 60 秒重新检查；核验超过有效期且无法刷新时，停止提供公开数据，展示暂不可用。
- GitHub 仓库变为 private、显式关闭公开功能或收到可信的公开性变更事件时，撤销公开快照并清理应用缓存。仅使用定期检查时存在检测延迟，不能承诺私有化的瞬间所有副本同时消失。
- 首版公开接口也使用 no-store，不使用不受控的 CDN 长缓存；服务器内可有短期结果缓存。已经被访客下载的公开数据无法召回。
- 游客只查询服务器缓存 / 数据库，不能触发 GitHub 全量同步。展示数据更新时间，首次尚无快照时显示空态，不伪装有实时数据。

## 4. GitHub 注册与登录流程

### 4.1 身份认证不等于成员登录

用户点击按钮，统一跳转 GitHub 官方 OAuth。通过 code / state 验证后获得 GitHub 固定用户 ID、用户名、头像等资料，以固定 ID 查询身份：

```text
游客 → 使用 GitHub 登录 / 申请加入 → GitHub 官方授权
                                      ↓
                            平台核验真实 GitHub 身份
                                      ↓
             ┌────────────────────────┼────────────────────────┐
      已获准且未停用              尚未获准                 成员已停用
             ↓                        ↓                        ↓
      建立成员会话             建立受限申请会话          提示联系管理员
      进入成员工作区            申请表 / 审核状态          不可重新申请绕过
```

“待审核用户已完成 GitHub 身份验证”不等于“可以登录成员工作区”。审核前的受限会话只能提交申请、查看自己的申请状态、退出，不接受普通成员业务 API。

### 4.2 首次申请

GitHub 回调成功后，未知用户先看到申请表，不在 OAuth GET 回调中默认替用户提交加入申请：

| 内容 | 来源 | 处理 |
| --- | --- | --- |
| GitHub 固定 ID、用户名、头像、主页 | 服务端 OAuth 验证结果 | 不允许用户手填或替换 |
| 姓名 / 团队昵称 | 用户填写，可选 | 与 GitHub 昵称分开 |
| 期望参与模块 | 用户填写，可选 | 仅申请意向，不授予职责或权限 |
| 加入说明 | 用户填写，建议必填且长度限制 | 供管理员判断，不渲染为可执行 HTML |
| 数据用途说明确认 | 用户明确确认 | 说明身份资料、申请和审核记录的使用 |
| 平台角色、成员状态、审核结论、飞书身份 | 不接受客户端填写 | 由服务端 / 管理员决定 |

用户显式点击“提交申请”后创建 pending 申请，显示提交时间、当前状态和“审核通过后可登录成员工作区”。

### 4.3 重复访问和已有成员

- 待审核者再次 GitHub 登录：进入原申请状态页，不重复创建成员或申请。
- 已批准者再次登录：建立正常成员会话；如是新审批成员，激活原有待激活成员记录。
- 被拒绝者：只能看对本人公开的反馈；按推荐 24 小时冷却重新提交，形成新申请轮次，不抹掉旧审核历史。
- 已停用者：联系管理员处理成员状态，不提供自助重申请恢复权限。
- GitHub 改名：更新展示快照，固定 ID 不变；旧用户名被另一账号占用不能复用原申请或权限。
- 已有管理员预录入白名单成员：继续直接登录激活，不强制重新申请。

## 5. 管理员审核

### 5.1 后台入口

增加“加入申请”菜单及待审核数量，列表展示 GitHub 身份、申请昵称、意向模块、说明、提交时间、当前状态；详情中提供 GitHub 主页入口。

支持待审核 / 已通过 / 已拒绝筛选和分页。首版逐条审核，批量通过暂不做，减少误放行。管理员不需要填写申请者的飞书 ID。

### 5.2 审核通过

推荐首版审核通过只授予**普通成员**资格。需要管理员角色时，后续使用现有成员管理流程单独提升，继续遵守最后管理员保护。

通过操作必须在一个数据库事务中：

1. 再次检查操作者正常且具有管理员角色，申请仍为 pending 且 version 匹配。
2. 使用申请已核验的固定 GitHub ID，创建或关联唯一成员，不依赖用户名重新决定身份。
3. 新成员进入现有 pending_activation，首次后续 OAuth 登录时激活；已存在正常成员不重复创建、不覆盖原角色。
4. 原记录已 disabled 时返回冲突，要求走专门的成员启用流程，不能借审批暗中恢复。
5. 申请标记 approved，记录 reviewer、reviewed_at、关联 member_id、公开反馈与内部备注，并写审计。
6. 提交成功后提示申请者“已通过，请使用 GitHub 登录”。

审核通过**不会自动把旧受限会话升级为成员会话**。用户重新经过 GitHub 登录获得全新成员会话，防止遗留会话或被盗申请 Cookie 静默获得权限。

### 5.3 审核拒绝与并发保护

- 拒绝必须填写可对本人展示的简要理由；管理员内部备注为独立字段，不能混用。
- 拒绝不创建成员、不绑定飞书、不修改任何 GitHub 仓库权限。
- 两个管理员同时处理同一申请，只有一个 version 条件更新成功；另一个返回 409，刷新后查看，不最后写入覆盖。
- 审批已经完成的请求重放不重复建成员；同一决定可返回原结果，冲突决定返回 409。
- 管理员预录入和申请审核共用成员授权服务；预录入遇到同一待审核申请，应明确确认并一并标记通过，避免“成员已获准但申请仍待审核 / 被拒绝”。
- 审批后的停用、重新启用、角色调整继续由成员管理处理；历史申请 approved 不意味着当前仍有成员访问权。

## 6. 状态与会话模型

### 6.1 分开保存申请与成员状态

```text
申请：draft（尚未提交） → pending → approved
                               └→ rejected → 冷却后新建申请轮次

成员：pending_activation → active ↔ disabled
```

draft 可仅存在受限会话 / 表单，不计为已提交申请。申请历史不可作为运行时权限缓存，运行时访问始终检查当前 members 的角色与状态。

| 身份 | 会话 | 能力与有效期建议 |
| --- | --- | --- |
| 匿名游客 | 不创建身份会话 | 仅公开读取，避免每次访问都生成数据库会话 |
| GitHub 已验证申请者 | registration session | 30 分钟绝对有效期；仅申请与本人状态，不能访问成员 API |
| 已批准正常成员 | member session | 沿用现有会话，7 天；每次请求实时核验成员状态 |
| 管理员 | member session + 当前 admin 角色 | 审批等敏感操作提交时再次核验权限 |

建议申请会话和成员会话使用不同 Cookie / 表或明确不可混淆的 scope。退出应同时清理本浏览器两类会话；OAuth 登录完成后轮换会话，不能根据请求中的 role / scope 建立权限。

### 6.2 申请状态页

展示已验证 GitHub 身份、申请时间、pending / approved / rejected、本人可见反馈，以及“返回公开概览 / 重新登录 / 满足条件时重申请”。

不展示个人中心、我的待办、飞书绑定或其他成员信息。状态页不接受任意 userId / applicationId 查询他人资料，主体由服务端会话决定。页面显示时可每 30 秒查询本人状态，过期后重新 GitHub 验证；不需要先绑定飞书才能知道审核结果。

## 7. 数据模型增量

保留现有 members / users / sessions / feishu_bindings，不把大量未知申请者直接塞入可分派成员目录。

| 实体 | 关键字段与约束 |
| --- | --- |
| registration_identities | 内部 ID、github_user_id 唯一、用户名 / 头像快照、首次 / 最近验证时间；不是平台成员资格 |
| registration_sessions | token_hash、identity_id、csrf、expires_at；仅受限作用域，不持久化 GitHub access token |
| join_requests | id、identity_id、status、申请昵称 / 模块 / 说明、submitted_at、reviewer_member_id、reviewed_at、public_feedback、internal_note、member_id、version、申请轮次 |
| public_snapshots / public_items | repository_id、generation、仅公开字段投影、生成时间、公开性验证信息；按批次整体替换 |
| settings | 注册开关、公开门户开关、公开性有效期、重申请冷却等；修改可审计 |
| audit_logs | 复用现有结构，增加申请提交 / 通过 / 拒绝、公开开关修改等动作；内部备注不能流入公开响应 |

核心约束：固定 GitHub ID 唯一识别身份；每个身份最多一个 pending 申请（部分唯一索引）；审批和成员创建同一事务；申请 / 成员编辑继续使用乐观 version；禁止按用户名模糊关联。

## 8. 接口设计（新增或改造）

下表是目标接口，不代表当前服务已经提供。

| 接口 | 访问范围 | 用途 |
| --- | --- | --- |
| GET /api/public/overview | 匿名可读，受公开开关和仓库公开性限制 | 仅公开统计、数据时间与对外可用状态 |
| GET /api/public/items | 同上 | 分页摘要，允许类型、GitHub 状态、标题 / 编号筛选；拒绝内部字段查询 |
| GET /api/session | 当前浏览器 | 返回明确的 guest / applicant / member 模式，成员 user 仅在真正获准时存在 |
| GET /auth/github | 所有人可发起 | OAuth 状态中记录登录 / 申请意图及受约束的站内返回页 |
| GET /auth/github/callback | OAuth 回调 | 验证身份后分流成员、申请者或停用提示；不自动提交申请 |
| POST /api/registration/applications | GitHub 已验证申请会话 | 显式提交加入申请，身份从会话取，客户端不能指定角色 / ID |
| GET /api/registration/status | 同上 | 仅返回本人最新申请与可公开反馈；无任意身份参数 |
| GET /api/admin/join-requests | 正常管理员 | 分页审核队列和数量 |
| POST /api/admin/join-requests/:id/approve | 正常管理员 | version 条件审批，原子创建 / 关联普通成员 |
| POST /api/admin/join-requests/:id/reject | 正常管理员 | version、publicFeedback、internalNote；拒绝并保留历史 |
| PUT /api/admin/access-policy | 正常管理员 | 配置注册 / 公开开关等策略；停止注册不影响已批准成员 |

受限会话的写接口同样检查 Origin 与 CSRF；匿名 GET 无需为游客生成 CSRF 会话。既有业务接口继续要求 active member，不通过“有任意 GitHub 会话”放宽 requireUser。

公开功能关闭返回明确的公开不可用状态；仓库私有 / 核验过期无法刷新时不返回内部快照。分页参数和排序字段使用允许清单，pageSize 建议最多 100。

## 9. 页面与交互

- `/`：公开概览和摘要列表；头部登录 / 申请入口。成员可点击进入工作区。
- `/join`：GitHub 验证入口；验证后出现提交表单和数据用途说明。
- `/join/status`：受限申请状态，不是个人中心。
- `/workspace`：已批准成员工作区，沿用当前任务、通知、个人设置与飞书流程。
- `/admin/join-requests`：管理员审核列表、详情和明确的通过 / 拒绝确认。

路径可按现有前端路由实现方式调整，但三类界面和后端权限不可混用。直接输入个人中心 / 管理接口地址不能绕过审核，游客深链接默认只打开公开摘要 / GitHub；待登录的内部深链接在 OAuth 状态中安全保留，仅允许本站路径，不接受外部任意跳转。

## 10. 审核通知与防滥用

### 通知

首版必须有后台待审核计数和申请者本人状态页。可以追加向选择接收运营提醒、已验证飞书绑定的管理员发送“有新的加入申请”，但管理员未绑定飞书不能影响审核功能。

申请者审核前尚无飞书通道，不承诺飞书推送审核结果，也不默认抓取 GitHub 私有邮箱发送邮件。后续邮件提醒应单独设计授权与用途。

### 防滥用

- 同一固定 ID 仅一个待审核申请；重申请建议间隔 24 小时，保留旧结论和审计。
- OAuth 发起、申请写入、公开列表分开限流，同时考虑 IP 与固定身份，避免共享 NAT 误伤整个团队。
- 设置申请队列容量阈值、内容长度限制与注册总开关；触发保护时暂停新申请，不关闭已有成员登录或游客公开读取。
- 公开访问不触发 GitHub 网络同步或飞书消息，不允许手动同步、任意搜索内部字段和无限页大小。
- 申请理由、头像、GitHub 昵称等均按外部输入处理，不执行 HTML / 脚本，不作为后台自动操作指令。
- 可在遭遇明显滥用后增加验证码等防护，不把用户知道某个 GitHub 用户名当作身份验证。

## 11. 与现有版本的兼容和迁移

1. 增加版本化表结构与策略配置，不清空已有成员、事务、绑定或通知。
2. 现有 active 成员继续登录，不要求重新审核；disabled 继续停用，pending_activation 继续代表管理员已预批准但未首次激活。
3. 申请 pending 与成员 pending_activation 不是同一状态，不能为了少改代码合并两者。
4. 初始管理员引导和管理员手工预录入保留；注册模块故障时管理员仍能管理现有团队。
5. 公开接口采用独立投影和权限链；不直接移除当前 `/api` 的登录中间件来实现游客模式。
6. 先在隔离环境验证申请流程和敏感字段，再生成首个确认公开的快照；没有合格快照时公开页显示空态 / 暂不可用。
7. 迁移完成前和灰度期间，公开数据开关默认关闭；验证后启用。注册开关与公开开关独立，可分别回退。
8. 演示模式继续明确是模拟数据；不能把演示自动管理员当作线上游客实现。

## 12. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| R01 | 匿名首次进入 | 无登录墙即可看允许公开的总体 PR / Issue；无个人中心，无自动管理员会话 |
| R02 | 游客越权 | 直接调用成员列表、内部事务、个人设置、写操作、同步和通知 API 均失败 |
| R03 | 数据公开边界 | 响应体、统计、筛选参数及浏览器网络请求均不包含内部负责人 / 工作流 / 申请 / 绑定等字段 |
| R04 | 注册身份真实性 | 用户经 GitHub 官方 OAuth；自报 githubId / role / scope 无法影响身份和权限 |
| R05 | 显式申请 | OAuth 回调只进入申请入口；点击提交才产生 pending；重复提交只有一条待审核申请 |
| R06 | 审核前隔离 | 受限申请会话只能操作本人申请；没有个人中心 / 飞书绑定 / 待办权限 |
| R07 | 审核通过 | 原子产生或关联唯一普通成员；申请者重新 GitHub 登录后才能获得成员会话 |
| R08 | 审核拒绝 | 不建成员；只显示本人可见反馈；重申请受冷却限制且保留历史 |
| R09 | 并发审批 | 版本冲突不覆盖另一位管理员的结论，不重复创建成员或发送提醒 |
| R10 | 旧用户兼容 | 已批准 / 预录入成员不被重新拦截；停用者不能重新申请恢复权限 |
| R11 | GitHub 改名 / 用户名复用 | 固定 ID 正确关联，另一账号不能继承旧申请或成员资格 |
| R12 | 私有仓库 / 过期核验 | 公开接口失败关闭，不返回内部缓存；开关关闭后应用缓存立即失效，记录检测延迟边界 |
| R13 | 本人申请隐私 | 猜测申请 ID、修改查询参数或使用另一申请会话无法获取他人理由、反馈或内部备注 |
| R14 | 回归 | 现有飞书绑定代次、成员停用、版本冲突、最后管理员保护和备份迁移测试继续通过 |

## 13. 实施顺序与待确认项

推荐分三步实施：

- **P1：注册审核**：受限身份会话、显式申请、管理员审核、批准后重新登录、现有成员兼容。
- **P2：游客门户**：独立公开快照、公开性门控、只读摘要 / 统计、首页分流与限流。
- **P3：加固与上线**：隐私字段回归、并发审核、私有化 / 缓存撤销、灰度开关和真实 OAuth 验收。

建议确认的产品细节：

1. 游客是否只看统计和摘要（本设计推荐），还是还要在本站看完整正文 / 评论。
2. 加入说明是否必填；团队姓名和意向模块是否保持选填。
3. 审核通过是否统一为普通成员（推荐），管理员角色另行提升。
4. 拒绝后的重申请是否采用 24 小时冷却；是否允许管理员明确禁止进一步申请。
5. 是否保留管理员手动预录入成员（推荐，兼容现有流程）。

**方案结论：开放“申请入口”，不开放“自动授予成员权限”；开放“GitHub 公开事务概览”，不公开“团队内部管理数据”。审核通过后再进入现有成员与飞书处理闭环。**
